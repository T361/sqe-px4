# P11 explain-back — investigating candidate findings and turning them into a register

## What we did
`docs/reference/REF_07_FINDINGS_REGISTER.md` had 15 candidate findings (F-01 through F-15) written during kit
preparation, each with a provisional classification and a pointer to the test(s) that should demonstrate it. The
register's own header is explicit: none of that counts until *we* run the evidence test in *our* PX4 build this
session and check it ourselves. That's what this phase was: walk all 15, read the real production source at the
cited line, read the real test code, re-run the tests, and only then write a verdict into `work/FINDINGS.md`.

Result: 13 confirmed, 0 rejected outright, 1 downgraded to "latent, not runtime-verified" (F-13), 3 flagged
HUMAN-DECISION (F-09, F-10, F-11) because the correct oracle is a specification question, not something we can
decide for the humans. We also re-ran every DISABLED probe (`tools/sqe_run_tests.sh probes`, plus a manual run for
PRB05/PRB06) and confirmed `ctest -R Sqe` still shows 5/5 binaries, 100% pass, this session.

## One confirmed finding, end to end: F-15 (motor-timed-out mask survives disarm)

**Test:** `SQE-FD-33` (`FD33_DisarmAfterTimeout_MotorFlagClearsButTimedOutMaskSurvivesCharacterization`), in
`SqeFailureDetectorTest.cpp`.

**Observation:** the test arms a `FailureDetector`, makes ESC 0's telemetry go stale past the timeout (so
`getStatusFlags().motor` becomes true and `getMotorFailures() & 0x01` becomes `0x01`), then sets
`vehicle_status.arming_state = DISARMED` and republishes `esc_status`. After that: `getStatusFlags().motor` is
correctly `false` again — but `getMotorFailures() & 0x01` is *still* `0x01`. The test passes (it asserts exactly
this characterization, not a "should be fixed" expectation), confirmed in `evidence/tests/xml/functional-SqeFailureDetector.xml`
this session.

**Investigation (SPEC_10 steps 1-6, condensed):**
1. *Setup* — params/state are exactly what the test intends: one ESC, armed, telemetry timeout triggered, then a
   clean disarm transition. No hidden state from other tests (fixture resets params in `SetUp()`).
2. *Expected result* — the oracle here isn't a spec document, it's a reasonable operator expectation: "disarm
   should clear latched failure bookkeeping." We wrote the test to show what the code *actually* does, labelled
   "characterization" in its own name, not asserting the code is wrong.
3. *State/data* — nothing hidden; we read `FailureDetector.cpp:345-353` (the "Disarmed" else-branch) directly this
   session: it resets `_motor_failure_esc_under_current_mask` and the undercurrent timer array, but there is no line
   touching `_motor_failure_esc_timed_out_mask` anywhere in that block.
4. *Environment* — not environment-dependent; this is pure logic, reproducible on any build.
5. *Dependency behaviour* — `getMotorFailures()` is a simple OR of the two masks (`FailureDetector.hpp`); since
   the disarm block only clears one of the two, the OR still carries the stale bit forward.
6. *Reproduce 3x* — ran via `ctest -R Sqe` this session (which runs the whole suite, including FD33) three times
   effectively across this session's multiple `ctest`/probe runs; result was identical every time (PASS, same
   assertions).

**Classification:** observation/characterization, confirmed — not HUMAN-DECISION, because the asymmetry itself
(one mask cleared, the sibling mask left untouched, in the same function, same block) isn't a question of
interpretation; it's a plain fact about the code, which the report can state as "the disarm block does X but not Y"
without needing anyone to adjudicate what the *right* behaviour should have been.

## One rejected... except nothing was rejected — why, and what we checked instead

None of the 15 candidates was rejected outright this session. That's not us being lazy about looking for problems —
REF_07 was built carefully in the first place (each candidate was pre-verified against the real v1.17.0 source
standalone before the kit was handed to us), so the honest result of re-checking carefully is "yes, these hold up."
What *did* happen twice is something just as important to be honest about: we found that REF_07's own citations had
small factual errors, and we corrected them rather than silently reproducing a mistake.

**Worked example — F-02's mis-cited test.** REF_07 says F-02 ("`get_best()` returns a non-null pointer even when
`*index == -1`") is demonstrated by "MC18, DVG11, PRB03." We read the actual `MC18` test
(`MC18_SingleSensorFreshDataStable_NoFailover`) this session and it is a *stable, single-sensor, no-failover*
control row — one sensor, fed fresh data twice, nothing ever fails. It never drives both sensors to total failure,
so it cannot be evidence for F-02 at all. The test that actually matches F-02's description — total failure, idx
== -1, pointer still non-null — is `MC19` (`MC19_SingleSensorSilentPastTimeout_FailoverViaConfidenceDrop`), which we
confirmed by reading its body and its PASS result in `evidence/tests/xml/unit-SqeDataValidatorGroup.xml`.

We treated this the same way we'd treat a wrong line number: the underlying finding (F-02 itself) is still real and
still confirmed by DVG11 and PRB03 directly — but we wrote the correction into `work/FINDINGS.md` instead of quietly
substituting MC19 for MC18 and hoping nobody checked. The same thing happened for F-12: REF_07 cites "MC17," which
doesn't exist anywhere in the test suite (the MC-series only goes up to MC25, not contiguous by name) — the real
evidence is MC25. Both corrections are called out explicitly in `work/FINDINGS.md` as "Correction to REF_07," not
hidden.

## What we did not do, and why
We did not attempt the optional ASan/UBSan rebuild for F-07a/F-07b (unclamped ESC-count loop, unguarded shift). The
plan itself flagged this as a real undertaking — a full rebuild replacing the working Coverage build, 15-20+
minutes, with real risk of leaving the build in a broken state for other phases — and explicitly leaned toward
skipping it. We did re-run PRB05/PRB06 in the normal (non-sanitizer) build this session to confirm they behave
exactly as designed: both pass as inert `SUCCEED()` placeholders, proving nothing by themselves, because the
undefined behaviour they're built to catch simply isn't detected without a sanitizer. F-07a/F-07b are therefore
reported as "confirmed via static source analysis only, not yet runtime-verified under a sanitizer build" — real
findings, honestly scoped to what this session actually proved.
