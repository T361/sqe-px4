# P06 explain-back — MC/DC derivation for DataValidatorGroup

## What we did
We derived, by hand, the MC/DC (Modified Condition/Decision Coverage) test matrix for the one component the
assignment requires full MC/DC on: `DataValidatorGroup`, specifically its 5 compound (multi-condition) Boolean
decisions. There was already a pre-derived matrix sitting in `docs/reference/REF_06_MCDC_PREDERIVATION.md` from kit
prep — our job was explicitly **not** to copy it, but to recompute every single row ourselves from the real source
code and only then compare. We read the actual `DataValidatorGroup.cpp` lines 140-311 again this session (not
trusting last session's notes), wrote small standalone Python scripts that mirror C++'s exact short-circuit
evaluation order for each decision, and ran every scenario's inputs through them to get the logical values (T/F),
the evaluation trace (including which operands get skipped — "NE" for not-evaluated — by short-circuiting), and the
final outcome. Every single value we independently computed matched REF_06 exactly — no discrepancies found in the
core logic. We did find and fix one explanatory error of our own while deriving a new scenario (see "one real bug we
caught in our own work" below) — it didn't change any test result, just a line of reasoning in the notes.

The output is `work/mcdc/mcdc_matrix.csv` (29 rows, 22 distinct planned tests, covering all 5 decisions) and
`work/mcdc/MCDC_ANALYSIS.md` (the write-up explaining why `DataValidatorGroup` was picked, the exact expressions,
the coupling proofs, the infeasibility proofs, and the observability classification). `tools/sqe_mcdc_check.py`
reports all 5 decisions COMPLETE.

## The 5 decisions, in plain terms
1. **DVG-D13** (`get_best()`, lines 187-190) — the "should this sensor become the new best one?" test. It's the
   biggest one: 7 atomic conditions combined as `((A&&B)||(C&&D)||(E&&F))&&G` — three different ways a sensor can
   "win" (suddenly became reliable; is clearly better and not lower priority; is about-equal but higher priority),
   all gated by "its confidence must be positive at all." This needed 12 test scenarios (minimum would be 8, but we
   kept all 12 for clarity, same choice REF_06 made, so each pair only differs in one thing and is easy to explain
   in the viva).
2. **DVG-D14** (line 203) — "did the best sensor actually change, or did everything just fail at once?" 3
   conditions, 5 scenarios.
3. **DVG-D15** (lines 207-208) — "was that switch a real failure, or just a higher-priority sensor coming back
   online?" 3 conditions, 4 scenarios. One of these (the "K=False" scenario) can't be observed through any public
   getter — its effect on `true_failsafe` never actually changes behaviour in that specific input combination — so
   that row is marked **O3** (structural evidence only: you'd show, via coverage, that a specific line did or didn't
   run) instead of O1/O2 (a direct return value or getter).
4/5. **DVG-D32/DVG-D34** (`failover_index()`/`failover_state()`) — the same 3-condition pattern appears in both
   functions ("is this sensor in use, does it have an error, is it the previously-best one?"), so we derived it once
   and reused the same 4 scenarios for both, just reading the result through two different getters.

## Why unique-cause, not masking
For every single one of the 5 decisions, we found a genuine **unique-cause** pair for every condition — meaning two
test scenarios exist where exactly one condition's truth value differs and every other condition in that decision
has the identical truth value in both scenarios. We never needed to fall back to masking (where other conditions are
allowed to differ as long as you can prove they can't affect the outcome). That's the stronger, easier-to-defend form
of MC/DC, and it's what the checker confirms for all 29 rows.

## Infeasible vectors — we don't write tests for impossible inputs
We proved (not just asserted) three combinations of DVG-D13's conditions can never happen, because of real
mathematical relationships baked into the code itself:
- `priority > max_priority` (F) forces `priority >= max_priority` (D) — basic number comparison.
- `confidence >= 0.9f` (B) forces `confidence > 0.0f` (G) — 0.9 is obviously bigger than 0.
- If `max_confidence < 0.9f` (A) AND `confidence >= 0.9f` (B), then `confidence` must be bigger than `max_confidence`
  (C) — because `confidence >= 0.9 > max_confidence`.
We did not write test scenarios for the opposite combinations (e.g. "F is true but D is false") — they're not
missing test cases, they're mathematically impossible inputs, and SPEC_04 says explicitly: never invent a test for
an infeasible vector, just document why.

We also independently re-confirmed (by re-reading lines 156-174 and 203-224) the two infeasibility proofs already
sketched in `work/basis/CFG_DataValidatorGroup_get_best.md`: `best != nullptr` can never be false when we reach that
check (DVG-D16), and the specific H=F/I=F/J=F combination for DVG-D14 is impossible because of how `max_confidence`
gets seeded on the very first call.

## One real bug we caught in our own work
While working out the exact bookkeeping for the `failover_index()`/`failover_state()` scenarios, we initially assumed
`_prev_best` (the "previous best sensor" bookkeeping variable) would stay at its startup value of `-1` through a
multi-call scenario. Re-reading lines 218-224 of the real source caught that this is wrong: on the very first ever
`get_best()` call, the code sets `_prev_best = max_index` (not `-1`), specifically so that bookkeeping gets
initialized without counting a false "failsafe" event. This didn't change which test result we'd observe (the
specific condition we were testing — "is this sibling's index equal to `_prev_best`?" — still came out False either
way), but it would have been a factually wrong explanation in the matrix notes if we hadn't caught it. We fixed the
note before finalizing. This is exactly the kind of thing the "re-derive yourself, don't just copy" instruction is
for — REF_06 didn't walk through this particular bookkeeping detail, so copying it would have propagated a gap we'd
then have had to defend wrongly in the viva.

## Float boundary caution (finding F-06)
`confidence()` computes `1.0f - error_density/100.0f` using 32-bit floats. We checked this directly: for example,
10 errors out of 100 gives `0.89999998...f` in real float32 arithmetic — not exactly `0.9f`. That means confidence
values generated this way can land on either side of the `0.9f`/`0.01f` thresholds depending on tiny rounding
behaviour, which could even differ between compiler optimization levels. We deliberately avoided picking any test
input that would land exactly on one of these quantisation boundaries — every confidence/priority value we chose is
comfortably (≥0.01-0.02) away from a threshold, so our MC/DC evidence won't become flaky or build-dependent.

## What this does NOT prove (say this honestly in the viva)
MC/DC coverage tells you each condition independently affects its decision's outcome — it does not tell you the
*thresholds themselves* are the right thresholds (is 0.9f really the right confidence cutoff? is 0.01f the right
"nearly equal" tolerance? we don't know, and MC/DC can't tell us), and it says nothing about decisions in code we
didn't derive MC/DC for (Areas A, C, D are covered to statement/branch level only).
