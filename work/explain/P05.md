## Walking `get_best()`'s CFG aloud (viva prep)
`get_best()` does two passes over the sibling list. **Pass 1** finds whichever sensor is *currently* selected
(`_curr_best`) and records its confidence as a "pre-check" baseline — this loop exits early via `break` the moment it
finds that sensor, so later siblings aren't even visited in this pass. **Pass 2** scans *every* sensor and asks, for
each one: "is this sensor good enough to become the new best?" — that's the big compound condition at lines 187-190,
with three ways to qualify (now-regular-when-it-wasn't, strictly-better-confidence-and-OK-priority, or
nearly-equal-confidence-but-higher-priority) all gated by "confidence must be positive at all." After the scan, the
function compares what it found to what was previously selected, and if they differ, works out whether that's a real
failsafe event (counted) or just a preference for a higher-priority sensor coming back online (not counted).

## Why the inner compound decision is only evaluated per loop iteration
Because it lives inside Pass 2's `while` loop body — it runs once per sibling, not once per `get_best()` call. With,
say, 3 IMU instances, that's 3 separate evaluations of the same decision in one call, each potentially with different
truth values for its 7 atomic conditions, because `confidence`, `max_confidence`, and `max_priority` all change as
the loop updates `best`. This is exactly why the MC/DC independence pairs have to be designed per-evaluation, holding
everything else about the scenario fixed — you're proving one condition flips the outcome of one evaluation, not
proving something about the loop as a whole.

## Two infeasible outcomes, explained with proofs
1. **`best != nullptr` (DVG-D16, line 213) is never False** when we actually reach that check. We only reach it when
   `pre_check_prio != -1` is True (that's the condition gating entry to this branch). But `pre_check_prio` only ever
   gets set away from its initial `-1` value inside Pass 1's "seed" block — and in that exact same block, on the
   very next lines, `best` also gets set to a real pointer. So by the time `pre_check_prio != -1` can be True,
   `best` has necessarily already been assigned. There's no code path where one happens without the other.
2. **`FI-D01`'s first operand being False** (`param_get(...) != PX4_OK` when reading `SYS_FAILURE_EN`) can't happen
   in this build, because `SYS_FAILURE_EN` is a parameter that's compiled into PX4's parameter table at build time
   (it's defined in `system_params.c`) — `param_find()` will always find it, so `param_get()` on a found parameter
   always succeeds. The only way to make this branch False would be to build a binary where that parameter
   definition was removed, which isn't something a test can do at runtime.
