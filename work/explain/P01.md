## Tag vs. commit hash — why they differ
`git rev-parse v1.17.0` printed `a5eb12d2ab591251faa009f76b2685b8cc64405d`. That is the **tag object**, not the commit —
annotated tags (the kind with a message/signature) are their own git object that *points at* a commit. The thing we actually
build is the commit it points to, which `git rev-parse 'v1.17.0^{commit}'` (or just checking out the tag) resolves to:
`d6f12ad1c4f70ad3230afd7d86e971421e02fef4`. If a report cites the tag object hash as "the commit we tested," that's wrong —
always cite the `^{commit}` value.

## Why `--recursive`
PX4 pulls several external projects in as git submodules rather than vendoring their code. Without `--recursive` those
directories stay empty and the build fails on missing headers. `git submodule status --recursive | grep -c '^-'` counts
submodules that are *not* checked out (a leading `-` means uninitialised) — we confirmed 0, i.e. all initialised.

once, interactively, on this machine. Everything else in P01 (the clone, the pinned commit, the branch) is already done
