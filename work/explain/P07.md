## Why DV-03 uses threshold 6 (the `>` boundary)
`confidence()`'s staleness check is `_value_equal_count > _value_equal_count_threshold` — strictly greater-than,
not greater-or-equal. We lowered the threshold to 6 (instead of the default 100) purely to make the boundary
reachable in a handful of `put()` calls. With 3 axes all holding the same value, each `put()` after the first
adds 3 to the one *shared* equal-count counter (one increment per axis, because the counter isn't per-axis).
After 3 puts the count is exactly 6: `6 > 6` is False, so it's *not yet* stale — confidence stays 1. One more put
pushes the count to 9, `9 > 6` is True, and now it is stale. This is exactly the "boundary value" testing
technique: we prove the `>` behaves as `>` and not `>=` by sitting a test exactly on the boundary.

## Why DV-05's "35" comes from 3 axes x 34 increments
DV-05 uses the *scalar* `put(timestamp, float, error_count, priority)` overload, which pads axes 1 and 2 with 0
every single call (`DataValidator.cpp` L47-51: `float data[dimensions] = {val}`). So every call after the first
has all three axes equal to the previous call (7.0, 0.0, 0.0 each time) — the shared equal-count counter gets +3
per call starting from call #2 (call #1 only initialises Welford state, it doesn't compare-and-increment). After
34 calls that's `3 * 33 = 99` (33 increments after the first call), still under the default threshold of 100, so
confidence is still 1. One more call (the 35th) brings it to `3*34 = 102`, which trips `102 > 100` and sets STALE.
This also demonstrates the header comment's claim that the equal-value count is "accumulated also between axes" —
it's one counter shared by all three axes, not three independent per-axis counters.

## Why DV-14 proves the density cap exists
`confidence()` caps `_error_density` at `ERROR_DENSITY_WINDOW` (100) the moment it exceeds that window
(`DataValidator.cpp` L125-128), but it never resets it to a *smaller* number — it just clamps the stored value to
exactly 100 and raises the HIGH_ERRDENSITY flag. A single put with error_count=101 isn't enough to prove the cap
actually caps anything, because the stored density could just as well have been left at 101 and we wouldn't see a
difference from the *outside* yet (confidence is `1 - density/100`, which would floor at 0 or go negative — we'd
need to inspect density directly to tell). DV-14's second put is what proves the cap: supplying the *same*
error_count again (101) makes DV-D01 ("error_count_in > _error_count") False, so the decay branch (DV-D02,
"density > 0 => density--") runs instead of the increase branch. If the density had really been left at 101 after
the first put, decrementing once would give 100, and `100 > 100` is still False this time around (no flag), with
confidence `1 - 100/100 = 0`. But what we actually observe is confidence ~= 0.01 and state 0 — which only happens
if the density after the first put was *capped to exactly 100*, and decrementing once gives 99, not 100
(`1 - 99/100 = 0.01`). That 0.01 is the fingerprint of the cap: it's the only value consistent with "density was
clamped to 100, then decremented by one on the next call."

## The two disabled probes
`DISABLED_PRB01` and `DISABLED_PRB02` assert the *stricter* behaviour a reviewer might expect (NaN streams should
reduce confidence; hitting the density window exactly should set a flag), which is the opposite of what DV-07 and
DV-15 prove the code actually does. Per R4 we never change an assertion to make a test agree with surprising
code — instead we kept both versions: DV-07/DV-15 are the confirmed characterization tests (F-09/F-10, they pass),
and PRB-01/PRB-02 are disabled probes that encode the "should" behaviour and are expected to fail when run
explicitly (`tools/sqe_run_tests.sh probes`), pending a human decision on whether F-09/F-10 are acceptable
quality gaps or real defects.
