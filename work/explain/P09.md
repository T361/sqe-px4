no fallback needed — same as `ModeManagementTest`).

## Why these need the functional level (not unit)
Unlike `DataValidator`/`DataValidatorGroup` (P07/P08), both classes under test read PX4 parameters **at
construction time** (`FailureDetector`'s `DEFINE_PARAMETERS` block, `FailureInjector`'s `param_get("SYS_FAILURE_EN")`
in its constructor) and communicate exclusively through uORB subscriptions/publications rather than plain function
arguments. That means every test must: set params with `param_set()` *before* constructing the object, publish the
uORB messages the object will read *before* its first `update()`, and only then call `update()` and assert. Getting
that order wrong silently tests stale/default state instead of the intended decision — SPEC_02 calls this out
explicitly, and `work/basis/SETUP_MAP.md` documents the same three-step ordering constraint we followed throughout.

## How the tests control time without lockstep
`px4_sitl_test` runs without PX4's lockstep scheduler, so `hrt_absolute_time()` is the real wall clock — there is no
way to "fast forward" it from a test. Every hysteresis-gated decision (roll/pitch attitude failure, external ATS,
ESC-armed mismatch, motor under-current) is driven by `systemlib::Hysteresis`, which only flips state after its
configured duration has elapsed continuously. We therefore lowered the relevant `_TTRI`/`_TOUT` parameters to their
documented minimums (`FD_FAIL_R_TTRI`/`FD_FAIL_P_TTRI` to 0.02s, `FD_ACT_MOT_TOUT` to 10ms) and then used
`std::this_thread::sleep_for()` for at least 1.5x that duration before re-publishing and calling `update()` again —
the "wait, then observe" pattern mandated by SPEC_02 §6/R11. The two fixed-at-300ms hysteresis cases (ESC-armed
mismatch, ESC telemetry timeout) can't be shortened by a parameter, so those tests pay the real 300ms+ cost — this
is why `functional-SqeFailureDetector` takes about 4.5 seconds to run (dominated by roughly a dozen tests that each
wait 150-700ms), versus single-digit milliseconds for the IMU and Injector binaries, which have no hysteresis.

## Why the IMU tests need their own binary
`updateImbalancedPropStatus()` reads `vehicle_imu_status`, a **multi-instance** uORB topic. PX4's `uORB::Subscription`
inside `FailureDetector` scans instances with `ChangeInstance()` across the full `ORB_MULTI_MAX_INSTANCES` range (10
in SITL) looking for the one whose `accel_device_id` matches the currently-selected accelerometer. For that search to
be meaningful, the test process needs real `PublicationMulti<vehicle_imu_status_s>` objects sitting on instances 0
and 1 for its entire lifetime — these are process-wide uORB device nodes, not per-test state, so they must be created
exactly once per binary (`SetUpTestSuite()`, in a fixed order: instance 0 first, then instance 1) and are never torn
down between individual tests. Mixing that into the main `SqeFailureDetectorTest` binary would mean every other
test's `FailureDetector` instance also sees those two IMU instances permanently "advertised", which would make the
no-detection tests (FD-equivalent) fragile and order-dependent — splitting the IMU group into its own binary keeps
that multi-instance state fully isolated from the other 34+13 tests.

## How FD31 proves the injector is in the detector's control path
`FailureDetector::update()` doesn't just call `_failure_injector.update()` for side effects and move on — it also
hands the **same** `esc_status` struct it just read from uORB to `_failure_injector.manipulateEscStatus(esc_status)`
*before* passing that struct into `updateEscsStatus()`/`updateMotorStatus()` (`FailureDetector.cpp` L70-82). FD31
exploits exactly that: it enables `SYS_FAILURE_EN`, warms up one ESC's "has reported current" latch, then injects a
STUCK failure for that ESC via a `vehicle_command`. On the next `update()`, the injector's `update()` consumes the
command and sets its internal blocked-mask; then, still inside the same `update()` call, `manipulateEscStatus()`
`memset()`s that ESC's telemetry (including its timestamp) to zero; then `updateMotorStatus()` runs on the now-blanked
struct and sees a zero/ancient timestamp, which it reads as a telemetry timeout — exactly the real detector branch
(FD-D33) we'd otherwise only reach by actually losing ESC telemetry. The test's assertion
(`getStatusFlags().motor == true` and `getMotorFailures() & 0x01 == 1`) only passes if the injector's mutation of the
struct really did reach the detector's own decision logic inside the same call — proving the two classes are wired
together inside `FailureDetector::update()`, not just two independently-testable components that happen to share a
header include.

## A real test-isolation bug we found and fixed in our own test code (not production)
The first run of `--gtest_shuffle --gtest_repeat=10` on `functional-SqeFailureDetector` failed FD31 on later
iterations (it passed alone, and passed as iteration 1, but failed from iteration 2 onward in the same process).
Per SPEC_10/R4 we stopped and investigated rather than loosen the assertion. Root cause: `vehicle_command` is a
*queued* uORB topic (`ORB_QUEUE_LENGTH = 8`), and a freshly-constructed `uORB::Subscription` is deliberately
positioned one generation behind the latest publication (`uORBDeviceNode::get_initial_generation()`, "allow the
subscriber to read" the most recent message) — exactly the documented "a new subscriber sees the last message ever
published as updated" semantics in `work/basis/SETUP_MAP.md`. Because FD31 is the only test in this fixture that
ever publishes a `vehicle_command`, and nothing in `SetUp()` was publishing a neutral one to clear that slot, the
*next* `FailureDetector`'s freshly-constructed `FailureInjector` would see the **previous iteration's leftover STUCK
command** as "new" during its very first (warm-up) `update()` call — before our own command was published — which
blanked the warm-up ESC telemetry early and prevented `valid_current_mask` from ever being set, so the real timeout
branch (FD-D33) could never fire later in that iteration. The fix was entirely in our test fixture: `SetUp()` now
publishes one neutral `vehicle_command` (`VEHICLE_CMD_DO_SET_MODE`, never matched by FD-D04) before every test,
exactly mirroring the pattern `SqeFailureInjectorTest::SetUp()` already used. After the fix, `--gtest_shuffle
--gtest_repeat=10` is stable (10/10 iterations, 0 failures) and every test also passes individually
(`tools/sqe_run_tests.sh isolation`: 34/34, 7/7, 15/15 alone). This was a bug in our own test isolation, not in
`FailureDetector`/`FailureInjector` — no production code was touched.

## A test-authoring arithmetic slip we caught and corrected (not a production defect)
FI05's expected `esc_online_flags` after a STUCK injection on ESC index 1 was first written as `0x0D`, which does
not match the test's own 4-ESC seed of `esc_online_flags = 0xFF` (all bits set). `0xFF & ~(1<<1) = 0xFD`, not
`0x0D` — a plain arithmetic mistake in our own catalogue-to-code translation, caught immediately by the first test
run (R4: the test disagreed with the real code, so it was investigated, not weakened). We corrected the expected
value to `0xFD` after confirming `FailureInjector::manipulateEscStatus()`'s real behaviour
(`status.esc_online_flags &= ~(1 << i)` on the matching loop index) independently against the source; no change to
`FailureInjector.cpp` was made.

## F-07 and F-08 were left as findings, not "fixed"
Two confirmed real defects from `work/basis/INVENTORY_FailureDetector_Injector.md` are deliberately **not** patched
in `FailureInjector.cpp` (R2 forbids it): F-07a (`manipulateEscStatus()`'s loop at L117 has no clamp to
`CONNECTED_ESC_MAX` unlike the sibling loop in `FailureDetector::updateEscsStatus()`) and F-07b (the same function's
`1 << i_esc` shift at L120 has no guard against a non-motor `actuator_function`, unlike `FailureDetector`'s own
FD-D31 guard for the identical situation). Both are encoded as `DISABLED_PRB05_EscCountAboveMax` and
`DISABLED_PRB06_NonMotorFunctionShift` in `SqeFailureInjectorTest.cpp` — they compile and, in this normal
(non-sanitizer) Coverage build, run to a `SUCCEED()` placeholder without crashing (undefined behaviour is not
guaranteed to crash without ASan/UBSan instrumentation), so they do not themselves prove the defects in this
session's evidence; they document the intended reproduction recipe for a future sanitizer build, per P11. F-08 (the
`FAILURE_TYPE_WRONG` log message printing `i` instead of `i+1`, a cosmetic log-only off-by-one, not a logic bug) is
noted in FI06's test comment but needs no probe since the actual bitmask logic (`1 << i`, not the log string) is
correct and already covered by FI06's assertions.
