# P03 explain-back — Coverage pipeline + baseline coverage

## What we did
Reconfigured the build in `Coverage` mode (`PX4_CMAKE_BUILD_TYPE=Coverage` — this adds `--coverage` and related GCC
flags, which instrument every compiled function to record which lines and branches actually execute). This is a full
rebuild of the whole PX4 build tree because it's a different compiler flag set, not just our files — that's why it
took longer than the plain P02 build. Then ran `tools/sqe_coverage.sh baseline`, which zeroes any leftover coverage
counters, runs all 147 upstream tests (none of ours exist yet), and merges an "initial" capture (so files with 0%
coverage still show up with their full line/branch counts, not missing entirely) with the "run" capture from actually
executing the tests.

## Line vs branch vs function counts in lcov
- **Line %** — fraction of executable source lines that ran at least once.
- **Branch %** — fraction of individual branch *outcomes* taken. A single `if` statement contributes 2 branch
  records (taken/not-taken); a compound condition like `a && b` contributes one branch pair *per operand* evaluated
  (gcov's short-circuit accounting), so branch % is really closer to "condition coverage of the operands gcov saw
  evaluated" than true MC/DC-style decision coverage — that's a different, stronger thing we measure separately in
  P06 for `DataValidatorGroup`.
- **Function %** — fraction of functions called at least once.

## Why gcov reports more "branches" than there are decision outcomes
Every short-circuit operand of `&&`/`||` gets its own pair of branch counters, plus loop conditions, ternaries,
`switch` cases (with an implicit default edge), and sometimes compiler-generated paths (e.g. the null-check GCC
inserts after `operator new` when built with `-fcheck-new` shows up as an "unexecuted block" marker, not a normal
branch pair). So a file's gcov branch count is always ≥ its count of decision *outcomes* as a human would count them
from the source — this is exactly why REF_03/04/05's "Obligations" sections state both numbers (e.g.
`DataValidatorGroup.cpp`: 38 decision IDs by hand-count, 116 gcov branch records) rather than treating them as the
same thing.

## Why the initial capture matters for 0% files
Without it, `FailureDetector.cpp`/`FailureInjector.cpp` — genuinely never executed by any upstream test — wouldn't
appear in the coverage report at all, because gcov only emits data for files that got *some* instrumentation hit
during the run. The "initial" (zero-count) capture, generated straight after the Coverage build before any test runs,
guarantees every scoped file shows up in `scope.info` with its true line/branch *denominator* even at 0% — otherwise
a reviewer couldn't tell "0% measured" apart from "forgot to include this file."

## Why baseline must precede student tests
This is the *only* trustworthy way to know how much of our scope's testing is actually new work versus incidental
side-effects of PX4's own test suite (e.g. `sitl-imu_filtering` happens to exercise `DataValidator`/`DataValidatorGroup`
a fair amount just by running the sensors module for 10 seconds, even though it was never written to test them). If
we captured coverage only after adding our tests, we couldn't separate "our tests did this" from "upstream already
did this" — which matters directly for the report's "test contribution" claims (R12: never overclaim).

## A note on an unrelated side effect we found and reverted
Running the full upstream suite under the Coverage build type (different compiler flags than the normal optimized
build) caused two EKF2 test golden-output files
(`src/modules/ekf2/test/change_indication/{ekf_gsf_reset,iris_gps}.csv`) to come out with tiny floating-point
differences in the 5th significant digit — not something we edited, just float rounding differing slightly under
`-O0`/coverage instrumentation versus the normal build. Reverted with `git checkout --` since only `Sqe*Test.cpp`
files and CMake additions are allowed to change (R2); logged as D-005 in case it happens again on a future run.
