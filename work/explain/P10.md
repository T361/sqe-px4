With all P07-P09 tests in place (108 active test cases across 5 GTest binaries: `unit-SqeDataValidator`,

## Why the branch percentage doesn't reach 100% — and why that's correct, not a shortfall
gcov's "branch coverage" counts **every short-circuit operand's own jump**, not just the decisions you'd draw on a
whiteboard — and critically, the compiler inserts extra "branches" of its own that have no meaning in your source
code at all. We found, by hand, three families of these and wrote them up with proof in `work/GAPS.md`:

1. **Exception-unwind edges** (`G-05`, by far the biggest group): every function call in C++ gets a hidden
   "what if this call throws an exception and we have to clean up" branch, even though none of these PX4 functions
   are written to ever throw. gcov counts the "it threw" side as a real branch that's "never taken" — but it is
   never *supposed* to be taken. We proved this with a tiny 10-line standalone test program outside PX4 entirely,
   built with the exact same compiler flags, and watched gcov label the same kind of edge `(throw)`.
2. **A `-fcheck-new` null check after `new`** (`G-01`): `DataValidatorGroup::add_new_validator()` checks
   `if (!validator)` after `validator = new DataValidator()`. On this Linux/SITL build, `new` never returns null on
   failure — it throws instead (that's the C++ standard's default behaviour) — so that null check is dead code
   *on this platform*, even though it would matter on an embedded target with a different allocator.
3. **A genuine gcov measurement bug** (`G-04`): `DataValidatorGroup::print()` has 6 small `condition ? "X" : ""`
   expressions as arguments to one `printf`-style call, spread across 6 source lines. We proved — by writing a
   tiny standalone reproduction and by temporarily adding (then removing) a debug print to confirm what the test
   actually printed — that gcov scrambles all 6 conditions' branch counters onto the *first* line of the call and
   loses track of which physical branch belongs to which condition. The text our tests check for (" OK", " STALE",
   etc.) really does get printed correctly; gcov's branch *counter* for that one specific case just can't be
   trusted. This is why `docs/specs/SPEC_03` tells us to report two numbers: the raw tool number, and a "feasible"
   number with these proven-bogus items excluded.

The remaining items are two families of **logical proofs** that a branch truly cannot be reached from any test
(not "we didn't think of a test" — "no test can reach it"):

- **DVG-D16** (`DataValidatorGroup.cpp:213`, `if (best != nullptr)`): we re-derived, by reading the function
  line-by-line, that every code path that reaches this `if` at all has already guaranteed `best` is non-null a few
  lines earlier, in the same `if` block. There is no way to get here with `best == nullptr`.
- **FD-D21/FD-D27** (`FailureDetector.cpp:194`/`:222`, `.copy()` returning false right after `.updated()` returned
  true): we traced through the actual uORB library source and proved that `.updated()==true` can only happen after
  at least one real `publish()` has already happened on that topic — and that same publish is what allocates the
  buffer `.copy()` needs. In a single-threaded test (which is everything we have), there's no way for that buffer
  to vanish between the two calls a few instructions apart.

## What we actually found and fixed (not just classified)
Three genuine gaps *were* closeable, and we wrote tests for them instead of writing proofs:
- **FD-D25** (`FailureDetector.cpp:212`): unlike FD-D21/FD-D27 above, this `.copy()` call is **not** preceded by an
  `.updated()` check — it happens after `ChangeInstance()`, which only checks that a uORB topic instance has been
  *advertised*, not that anything was ever *published* to it. We proved (by reading the uORB device-node source)
  that "advertised but never published" is a real, reachable state, and wrote `SQE-FDI-08` to construct it: a third
  IMU-status publisher that calls `advertise()` but deliberately never calls `publish()`.
- **FD-D38 and FD-D41** (`FailureDetector.cpp:313` and `:324-326`): two 3-condition `&&` decisions in the
  under-current motor-failure check. Existing tests only ever drove the *first two* conditions false; the *third*
  condition of each (`!esc_timed_out`, and "the failure mask bit isn't already set") had never been tested while
  the first two were true. We wrote `SQE-FD-36` and `SQE-FD-37` to engineer exactly those scenarios.

One of our own test-design mistakes, found and fixed before it ever produced a wrong number: our first draft of
SQE-FD-36/37 asserted on a bitmask value (`0x02`) that we believed meant "the under-current failure flag for ESC
0", based on a wrong assumption that the timed-out and under-current failure trackers used different bits per ESC.
Re-reading `FailureDetector.hpp`'s `getMotorFailures()` showed both trackers share the *same* bit per ESC (there's
only one ESC in our test, so bit 0 for both) — we rewrote the tests to check behaviour through timing instead of a
bitmask value, and verified the corrected tests before taking any coverage capture with them.

## Predicting what coverage would drop if a test were removed
We ran every DataValidatorGroup test alone, with coverage zeroed first, to see exactly which lines/branches *only*
that one test reaches (`tools/sqe_coverage.sh pertest-all`, output in
`evidence/coverage/pertest/unit-SqeDataValidatorGroup/unique_coverage.md`). The short version: most of our 35 tests
overlap heavily (many scenarios walk through the same `get_best()` loop), so removing most of them individually
wouldn't drop coverage at all — other tests already reach the same lines. But two tests stand out:

- **If `SQE-DVG-MC13` were removed**: `DataValidatorGroup.cpp:303` (1 line) and two branch outcomes at lines 301
  and 302 would go uncovered. MC13 is the "sensor 0 times out, sensor 1 takes over — a *real* failover is
  reported" scenario; it's the only test in the whole suite that drives a genuine failover with the particular
  combination of flags that light up those specific lines in `print()`'s status output — nothing else in the
  catalogue reaches that exact combination.
- **If `SQE-FD-23` were removed** (bonus check, FailureDetector binary): one branch outcome,
  `FailureDetector.cpp:288 b0.5`, would go uncovered — the specific edge in the ESC-telemetry-timeout state
  machine where a *second*, still-stale sample arrives after the timeout flag is already latched (proving the
  flag doesn't get needlessly re-set). No other test republishes a still-stale sample a second time.

This matters for the viva: it's not enough to say "we have 108 tests" — we can point to the *specific* line each
test uniquely earns, which is exactly the kind of question a strict examiner asks ("what would you lose if I
deleted this test?").
